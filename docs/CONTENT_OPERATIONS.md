# memware GitHub 内容运营手册

本手册把 GitHub 仓库当作产品的首个增长页面，而不只是代码容器。当前阶段是**预发布验证期**：先保证每个对外承诺都可体验，再扩大曝光。

## 1. 北极星与阶段目标

**北极星行为：** 新用户在 15 分钟内完成安装、成功运行 `memory_status`，并在一个真实会话中完成一次自动写入与一次召回。

当前 4 周交付目标（不是增长基线）：

1. 完成 npm 主包、平台包和首个 GitHub Release 的可安装发布。
2. 获得 5 位非维护者的完整首体验记录。
3. 沉淀 3 个可公开的真实案例，覆盖长期开发、跨会话任务和本地优先工作流。
4. 所有公开内容只使用经过验证的命令、平台和能力口径。

## 2. 目标用户与一句话价值

| 优先级 | 用户 | 核心痛点 | 内容承诺 | 主 CTA |

| P1 | MCP / Agent 构建者 | 记忆能力耦合在单个应用中 | 7 个标准 MCP 工具，可接入自己的 Agent | 查看工具与架构 |

每篇内容只设置一个主 CTA，避免同时要求 Star、安装、提 Issue 和加入讨论。

## 4. 四类内容支柱

1. **用户问题**：重复自我介绍、跨会话丢失、团队 Agent 上下文断裂。
2. **产品证据**：真实命令、一次写入/召回演示、平台测试结果、性能或质量数据。
3. **信任边界**：什么保存在本地，什么会发往模型接口，如何隔离与删除。
4. **构建过程**：架构取舍、MCP 工具设计、Hook 可靠性、兼容性进展。

选题必须至少回答“用户为什么在意”和“有什么可验证证据”。纯功能罗列不进入发布队列。

## 7. 发布门槛

任何带安装 CTA 的内容发布前必须满足：

- 公共 npm registry 能解析 `memware@latest` 及对应平台包。
- GitHub Release 附件与校验信息可访问。
- 在干净环境分别完成 macOS arm64、Linux x64 安装烟测。
- `memory_status`、一次写入、一次召回均有成功证据。
- README、npm README、Release Notes 使用同一命令和版本号。
- 已说明平台、模型接口和数据边界，不使用“完全离线”表达。

任一项未满足时，内容 CTA 只能指向源码体验或体验者招募，不能引导 `npx` 安装。

## 8. 单次发布的复用流程

1. 从用户可感知变化中确定一个主叙事，不以 Commit 列表作为标题。
2. 用 [`RELEASE_POST_TEMPLATE.md`](content/RELEASE_POST_TEMPLATE.md) 形成事实母稿。
3. 先生成 GitHub Release Notes，再压缩成社区短帖和案例更新。
4. 每个渠道保留同一个证据链接与主 CTA。
5. 48 小时后记录曝光、访问、安装成功、有效反馈与失败原因。
6. 把高频问题回写 README/排障，把真实用法回写案例库。

## 9. 可采集指标看板

memware 默认不增加产品遥测。指标只来自 GitHub 的仓库级聚合数据和体验者主动提供的结果，不收集 API Key、用户记忆、原始对话、个人路径或本地数据库。

| 层级 | 指标与定义 | 数据来源 | 负责人 | 节奏 |
| --- | --- | --- | --- | --- |
| 发现 | 仓库 Views、Unique visitors、Referring sites、Clones | GitHub Insights → Traffic 的聚合数值 | 仓库维护者 | 每周一快照 |
| 关注 | Star、Watch、Fork 的期末值与净变化 | GitHub 仓库公开页面与 Insights | 仓库维护者 | 每周一快照 |
| 激活 | 自愿反馈中成功运行 `memory_status` 的非维护者人数 | Discussions 体验反馈；只记录聚合计数 | 仓库维护者 | 收到反馈后登记，周汇总 |
| 价值 | 自愿反馈中完成一次自动写入与一次召回的人数 | Discussions 体验反馈；不收集记忆内容 | 仓库维护者 | 收到反馈后登记，周汇总 |
| 质量 | 首次尝试失败人数 ÷ 提供完整结果的体验者人数；同步记录主要失败原因 | Bug、Documentation report、体验反馈 | 仓库维护者 | 每周复盘 |
| 参与 | 有效 Issue、Discussion、外部 PR 数，以及首次维护者响应时长 | GitHub Issues、Discussions、Pull requests | 仓库维护者 | 每周复盘 |
| 留存 | 自愿反馈者中，第 7 天仍确认使用的人数 ÷ 可回访人数 | 一次自愿的 7 日回访；不做后台追踪 | 仓库维护者 | 每位体验者最多回访一次 |
| 内容质量 | 双语生成一致率、内容检查通过率、失效链接修复时长 | `bun run content:check` 与相关 Issue | 仓库维护者 | 每个 PR + 每周汇总 |

每周使用 [`METRICS_SNAPSHOT_TEMPLATE.md`](content/METRICS_SNAPSHOT_TEMPLATE.md) 生成一份仓库内快照。GitHub Traffic 是滚动窗口，因此应固定节奏记录；如果某周无法访问数据，明确写 `N/A`，不能用 0 代替缺失值。

### 基线规则

- 2026-08-29 的线上状态是启动快照：0 Star、0 Fork、无 Release、npm 无公开包；它不是完整统计窗口。
- 先记录两个完整周窗口，再确定增长目标、渠道优先级和内容胜负标准。
- 少于 5 位完整体验者时，激活、质量和留存只报告原始人数与分母，不发布百分比。
- 任何体验反馈都必须自愿；拒绝反馈不影响产品使用，不得为了指标加入隐形遥测。

## 10. 实验与内容节奏

建立两个完整基线窗口后，每次只改变一个主要变量：

| 日期 | 假设 | 内容/入口变化 | 目标指标 | 结果 | 决策 |
| --- | --- | --- | --- | --- | --- |
| YYYY-MM-DD | 示例：首屏强调“自动写入”会提高完整体验人数 | README 标题 A → B | 完整体验人数 | 待记录 | 保留/回滚/继续 |

- **周更新**：只有出现用户可感知变化、真实案例或重要失败修复时才发布；使用 [`WEEKLY_UPDATE_TEMPLATE.md`](content/WEEKLY_UPDATE_TEMPLATE.md)。
- **月度快照**：至少积累 4 个周快照后再发布，汇总产品变化、反馈、质量和验证边界。
- **版本发布**：只在用户可感知版本交付时使用 [`RELEASE_POST_TEMPLATE.md`](content/RELEASE_POST_TEMPLATE.md)，提交数量本身不构成发布理由。
- 连续两个完整窗口没有带来激活或有效反馈的内容主题应降级；能稳定带来端到端成功的主题再扩展为案例、教程和 FAQ。
